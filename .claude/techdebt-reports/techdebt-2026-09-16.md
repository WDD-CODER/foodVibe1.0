## Detailed Findings

### Dead Code — npm dependencies

**Confirmed zero references anywhere in the repo (safe now, pending human sign-off):**
| Package | package.json | Evidence |
| --- | --- | --- |
| `@angular-eslint/builder` | root (devDep) | No `ng lint` architect target in `angular.json`; `lint`/`lint:fix` scripts call the `eslint` CLI directly. Confirmed by manual grep + `depcheck` + `knip` independently. Removed 2026-09-16, `ng build` + `ng test` verified clean. |

**Correction — removed in error, reinstated:** `@angular/platform-browser-dynamic` was initially flagged as zero-reference by manual grep, `depcheck`, AND `knip` alike, and removed. CI's `test` check then failed: `ng test`'s Karma builder generates a synthetic entry file (`ng-virtual-main.js`) at build time that imports `@angular/platform-browser-dynamic/testing` to bootstrap Angular's TestBed — this import exists only in a build-time-generated virtual module, never in any real source file, so none of the three checks (which all work by scanning real files) could see it. Reinstated at the same `^19.2.21` pin; `ng test` (311/311 passing) and `ng build` reverified. **Lesson for future dependency audits on this repo:** any of the three checks used here can produce false negatives for packages only consumed by a build tool's own generated code (Karma's test entry is one instance; there may be others — e.g. Angular's dev-server or i18n extraction tooling). Always run the full local `ng test` + `ng build` suite, not just `npm run build:render`, before trusting a "zero reference" finding on an `@angular/*` package.

**Needs human decision (tool-flagged, plausible but not 100% certain):**

| `@typescript-eslint/eslint-plugin`, `@typescript-eslint/parser` | root (devDep) | `eslint.config.mjs` only imports the bundled `typescript-eslint` wrapper package, which already re-exports both. | The wrapper may still resolve these as peer deps under the hood — verify `npm ls @typescript-eslint/parser` before removing. |
| `autoprefixer`, `postcss` | root (devDep) | No `postcss.config.*` in the repo; `@angular-devkit/build-angular` ships its own nested copies. | Angular's CSS pipeline may still read a user-level copy if present; low risk either way but not zero. |

| Package | Why flagged | Why it's actually used |
| --- | --- | --- |

| `cross-env` (server) | `depcheck` flags it | Used directly in `server/package.json` scripts (`dev`, `dev:local`, `dev:remote`) — `depcheck` doesn't scan the `scripts` field. |
| `eslint` (server) | `depcheck` flags it | `server/eslint.config.mjs` exists and is a real config, but no `server/package.json` script currently runs it — see gap below, not a removal candidate. |

**Minor gap (not dead code, opposite problem):** `server/eslint.config.mjs` exists but no npm script in `server/package.json` invokes it. Either add a `lint` script there or accept it's used ad hoc only — human call, no urgency.

**Undeclared dependencies (correctness risk, not size):** `knip` flagged `mongodb` and `dotenv` as used-but-unlisted in root `package.json`:
- `scripts/backup-before-repair.mjs`, `scripts/diagnose-broken-refs.mjs`, `scripts/repair-recipe-references.mjs` all `require`/`import` `mongodb` and `dotenv` directly, but neither appears in root `package.json` dependencies (only in `server/package.json`). These scripts currently work only because npm's hoisting happens to put `server/node_modules`'s installs where Node can resolve them from root — fragile, could break on a clean `npm ci` without `server/` installed first, or on a package-manager change. Recommend adding both as root devDependencies (or moving these 3 scripts under `server/`) in a follow-up — flagged here, not fixed in this audit-only pass.

### Bundle Size — production build measured (previously never run)

`ng build --configuration=production` (clean build, this session):

- **Initial bundle: 593.77 kB, exceeds the configured 500 kB budget by 93.77 kB.** This is a live, currently-true violation — the build only *warns*, it doesn't fail, so this has been silently over budget with no one alerted.
- Initial bundle is composed mostly of unnamed vendor/shared chunks (largest: 168.11 kB, 82.88 kB, 44.63 kB raw — `main` itself is only 69.72 kB). Because these chunks have no `Names` entry in Angular's own build report, and `source-map-explorer` cannot parse esbuild's source-map format (0% of every chunk mapped — a known tool/builder incompatibility, not a repo problem), their exact module composition is still unknown. **Follow-up needed:** try esbuild's own `--metafile` output (Angular's esbuild-based application builder may support emitting one) instead of `source-map-explorer`, which is built for the older webpack pipeline.
- Largest lazy chunk by far: `exceljs-min` at 947.36 kB raw / 217.57 kB transfer. Already correctly lazy-loaded (only fetched on an export action, per plan 302 M1's `await import('exceljs')` conversion) — not urgent, but by far the single biggest chunk in the app if it ever stopped being lazy.
- `cook-view.page.scss` inline style budget also over: 22.11 kB vs 20 kB (2.11 kB over) — pre-existing, unrelated to this session's changes.
