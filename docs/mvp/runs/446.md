## Decisions
- The freeze rule (`snapshotActionOnStage`) is defined once in `shared/schemas/entities/event-stage.ts` and used by both the client (`snapshotOnStageChange`) and the events router (via `server/generated`) · one rule, no drift; the file is in scope.
- On entering "ביצוע" the client sends a fresh snapshot and the server freezes that one (the stored one only when none is sent) · the plan's "attach `buildFor(event)` when the action is not none"; the chef freezes the plan of the moment of the move.
- `plannedProfitPct` is `0` when the planned revenue is 0 (schema field is a number) and `accuracyPts` is `null` then · C-SNAPSHOT types it as a number.
- `missingAmounts` counts only rows with a planned amount above 0 and no typed payment · a "ללא ספק" row planned at 0 would otherwise block "partial" forever.
- Closing writes are accepted from any stage except "הסתיים" (409), as long as the event has a snapshot or a closing (else 400 `NO_PLAN`) · the plan only names the finished lock; the dialog is offered from "ביצוע" on.
- Closing rows are matched by `supplierId` (null = "ללא ספק"); two rows with the same supplier -> 400 `DUPLICATE_SUPPLIER` · amounts and rows must be comparable for the owner/staff split.
- A change to a row's `planned` or `name`, or adding or removing a row, counts as a money change (owner only) · it moves the profit.
- `POST /:id/refresh-plan` on an event with no snapshot stores it frozen when the event is in "ביצוע" / "פוסט-פרודקשן", and re-syncs the planned amounts of existing closing rows (typed values stay, new snapshot suppliers get a row) · a refreshed plan and its closing rows must not disagree.
- The generic POST drops any `planSnapshot`; the generic PUT drops a client `frozenAt` and the whole snapshot when the stored one is frozen · only the events router freezes.
- `MenuEventSaveService.prepareForSave` takes the live plan with or without `rawLines` (`LivePlan` type); without raw lines `PlanSnapshotService` runs the engine · keeps the existing 445 spec call shape valid.
- Overrun text shows `חריגה של 15% (₪150.00)` (money formatted by `formatMoney`, the only allowed formatter) instead of the plan's `(150 ₪)` · run-mode rule on money formatting.
- A decrease shows `-2.5% (₪-50.00)` in grey without a dictionary key · it is only numbers.
- Added four dictionary keys beyond the plan table: `closing_accuracy`, `closing_pick_supplier`, `closing_photo_open`, `closing_photo_remove` · accuracy line in the footer, picker placeholder, two aria labels.
- «הוסף ספק» uses `app-custom-select` (typeToFilter) over the business suppliers not yet in the table, plus the "ללא ספק" entry when absent · run-mode "Reuse first".
- «סגירת אירוע» is a link in the stage bar's link row, shown for "ביצוע", "פוסט-פרודקשן" and "הסתיים" · a finished event can still be opened to look at it or to reopen it.
- `PUT /:id/stage` to "ביצוע" etc. still needs `changeStage` (staff: own events only) as in plan 442; finish, reopen and refresh-plan need `editMoney` (owner) · plan decision.
- Staff may still send `planSnapshot` through the generic PUT of an event they created (it is not a money field) · the snapshot only changes while not frozen; making it owner-only needs `shared/schemas/money-fields.ts`, outside scope.
- The dialog saves on every field change (whole closing, one request at a time in order) and falls back to the stored closing when the server refuses · no separate "save" button; the plan has none.
- Not measured in a browser: the phone full-height sheet and the camera flow (MongoDB down, app empty). The cards cover them.
