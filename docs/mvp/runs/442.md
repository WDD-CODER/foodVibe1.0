## Decisions
- Client `menu-event.model.ts` declares `EventStage`, `NotClosedReason`, `EventStageEntry`, `EventNote` itself instead of importing from `shared/` · no client file imports `shared/schemas` today (it is compiled for the server only); the list is mirrored with a comment.
- `events.js` has its own copy of the write rate limiter (15 min, `DATA_WRITE_LIMIT_MAX`, `0` = off, per user) · `generic.js` does not export its limiter and a shared util is outside the plan scope; same budget as the data router.
- A note edit or delete is authorized with `addNote` on the event, then the author check (`note.by === userId`, else 403 `FORBIDDEN`/`no_permission`); the Mongo filters repeat `by` so a race cannot touch another person's note · defence in depth.
- `PUT /:id/stage` to the current stage returns 200 with the event unchanged, no history entry · plan: "same stage -> ok, no history entry".
- A token without `name` stamps `byName: ''` (the schema requires a string) · real tokens always carry `name` (C-USER).
- A stage move and a note write validate the would-be stored document with `checkStoredDoc` before the write (INV-4), so an old event that already violates the schema is refused with 400 `Validation failed` instead of being half-fixed.
- Generic `POST /menuEvents` always resets the event to `inquiry` with a fresh history, so an event re-posted by the client with its own `_id` (restore from trash, `appendExisting`) loses its stage · the plan says a generic POST starts every new event in inquiry; plan 443 should use `PUT .../stage` after creation if it ever needs another start stage.
- `notClosedText` and `reasonText` are trimmed and cut at 2,000 characters, omitted when empty · matches the schema max.
- Migration 0008 sets `updatedAt` on the events it touches · same as 0007. It treats `stage: { $exists: false }` as the only marker, so trashed and master events are staged too.
- Contract extension logged in `docs/mvp/mvp-map.md` (function exports, client types, error codes, response shapes).
