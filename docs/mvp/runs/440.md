## Decisions
- Rehearsed on `--db=` scratch DBs on a throwaway mongod (local service stopped) instead of `--write=yes --backup-dir` against the shared local DB · run mode forbids touching shared data, and the backup check applies only to non-scratch DBs.
- Atlas copy = the existing read-only snapshot `atlas-2026-10-20T15-32-31` (no new Atlas read) · it is v2-shaped but `menuEvents` is empty there (its 8 events sit in the legacy `MENU_EVENT_LIST`), so that rehearsal patched 0 events; event snapshots were exercised on the local copy and the unit tests.
- Folds apply to every business-own `eventType`/`menuType` term whose kind + key is one of the six seed keys (master has it or gets it now), not only to just-inserted keys · a run that crashed after the insert still folds on the next run (idempotent).
- A preparation whose recipe is not in the list counts as portion-unit (rounded up) · the safe side for food amounts.
- `masterSeedDocs(existingKeys, now, maxSortByKind)` takes a third parameter for the sort order after the last master term of the kind · the plan requires "after the last master term".
- `portionsChange` reports per item `{ _id, name, businessId, section, recipeId, stored, recomputed }` and always lists, also on re-runs · it is a report, not a step.
- Every doc the migration changes gets `updatedAt` = migration time · keeps sync ordering honest.
- The Hebrew event-type names are seeded as keys, no dictionary entries (plan); `chef_plated_front` is appended under `general` in the dictionary.
- Contract extension logged in `docs/mvp/mvp-map.md` (`defaultCoefficient`, `ItemPortions`, `coefficientSchema`, `TypeSnapshot`).
