## Decisions
- Base hook instead of copied overrides: `BaseEntityDataService` takes a third constructor argument `EntityLoadOptions` (`errorEvent`, `errorMessage`, `clearOnReload`) and a `protected normalizeRow(row)` hook · keeps each service's own hydrate log event, recipe/dish "empty the list on reload" and dish/product legacy normalisation without re-copying the load block (plan: "change the base only if it lacks a hook a copy needs"). Equipment/supplier/venue unchanged (defaults keep their old behaviour).
- Recipe/dish/product `reloadFromStorage` now goes through the base (`ensureLoaded` with a shared in-flight promise) instead of calling `loadInitialData` directly · same data, same signal, same `hasLoaded()`; the only difference is that a concurrent `ensureLoaded()` during a reload now shares the request instead of firing a second fetch. Recipe/dish still empty the list first (`clearOnReload: true`); product and menu-event do not.
- S1 landed as one commit (not one per service) and S2-S6 as one commit · S2-S4 must land together (callers break) and S5/S6 both edit `unit-registry.service.ts`; `ng build` passed before each commit.
- `productUnitAdded$` / `awaitProductUnitAdded()` (plan 423, after the plan was written) converted the same way: `Promise<ProductUnitAdded | null>`, `null` on close or when the save was not in product mode · plan P0 says "no RxJS" in the unit registry; leaving one Subject would keep `Subject`/`take`/`takeUntil`.
- Waiters are a private list of resolvers settled once on save (key) or on `closeUnitCreator()` (null) and then cleared · same "first result only, nothing after the window closes" semantics as `take(1)` + `takeUntil(creatorClosed$)`.
- `product-form` `pickNewUnit_` drops `takeUntilDestroyed`: it watches `destroyRef.onDestroy` and does nothing if the form was destroyed before the window answered · the old code restored the previous value on a destroyed form (invisible); now it skips it.
- `ai-draft-editor` `openUnitCreator_()` now takes the `onSaved` callback instead of returning an Observable · keeps its three callers one line each and the null check in one place.
- Callers that subscribed with `{ next, error: () => {} }` became `.then(...).catch(() => {})`; callers with no error handler (`rate`, `toggleApproval`, `toggleFavorite`, cook-view rating) keep no handler (an error stays unhandled as before, after the same toast).
- `recipe-row-actions.remove()` and the cook-view/recipe-builder/product-form save functions now resolve after the save finishes instead of right after starting it · their callers (templates, `onApproveStamp`) do not await them, so nothing visible changes.
- `TaxonomyStore.loadSafely(log, { track })` / `reloadSafely(log)` take the facade's own `{ event, message }` · every facade keeps its existing log event name (`crud.metadata.hydrate_error`, `crud.preparations.load_error`, `crud.units.hydrate_error`, `crud.equipmentCategories.load_error`, `crud.menuEventTypes.load_error`, `crud.menuSectionCategories.hydrate_error`). The store's private helper is `logFailedLoad` so `grep logLoadError` stays empty. `preparation-registry` and `menu-section-categories` lost their now-unused `LoadingService` injection (`track: true` does it).
- Scope additions (small, required by the plan): `cook-view.page.spec.ts`, `recipe-ingredients-table.component.spec.ts`, `coefficient-manager.component.spec.ts` (mocks of the changed call shapes) and `docs/brain/component-families.md` (run 450: refactors must update the registry when a copy is gone; `entity-data-service`, `kitchen-state`, `taxonomy` families now say "Known copies: none"). Added to the plan's scope block.
