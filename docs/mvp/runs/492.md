## Decisions
- Soft delete with a released username, not a hard delete: the record stays (refresh answers `USER_REMOVED`, plan 428's friendly login message, and `createdBy` ids keep an owner), only `name` moves to `removedName` and becomes the tombstone `<name>~removed~<_id>` (`~` never passes `isValidUsername`; the id keeps it unique; the unique index is unchanged). The report's title says "DB cleanup"; this delivers the asked outcome (reusable username) without dropping the record.
- The report's "no new Atlas migrations required" line predates this fix: the Final gate below is a one-off data release the Human runs after deploy (no schema or index change). Without it, staff removed on production before the deploy keep their names blocked.
- Login fallback (`auth.js`): only when no live user has the typed name, finds the latest `{ removedName: name, removedAt != null }` user, runs the same `verifyPbkdf2`; match → 403 `USER_REMOVED`; otherwise (wrong password, no hash, nobody) the same 401 `Invalid credentials` as an unknown user. No `failedAttempts`/`lockedUntil` written on the removed record.
- DELETE also fixes a legacy removed user (has `removedAt`, no `removedName`) and keeps its original `removedAt`; a second DELETE on a fully released user writes nothing.
- Tests: `teamLimiter` (10 adds per owner) and `loginLimiter` (10 per IP) are shared across the file, so the new `business-team` cases use a fresh owner id per test and at most 3 wrong-password logins.
- No file outside the Read-Write Scope was changed.
