## What shipped (Milestone 1 — do first)

**Server**
- `server/constants/searchable-entity-types.js` (new) — `SEARCHABLE_ENTITY_TYPES =
  ['PRODUCT_LIST', 'RECIPE_LIST', 'DISH_LIST']`, shared by db.js and generic.js.
- `server/db.js` — `{ userId: 1, name_hebrew: 1 }` compound index on each searchable
  type (idempotent, runs at connect like the existing indexes).
- `server/routes/generic.js` — `GET /:type/search?q=&limit=`, registered before
  `GET /:type/:id`. Allowlist-gated to `SEARCHABLE_ENTITY_TYPES` (403 otherwise).
  Case-insensitive-only-for-Latin anchored regex on `name_hebrew` (Hebrew queries stay
  case-sensitive/plain so they can use the new index; Latin queries add the `i` flag,
  matching `filterOptionsByStartsWith`'s client semantics). Lean projection per type:
  Product → `_id, name_hebrew, base_unit_, purchase_options_`; Recipe/Dish → `_id,
  name_hebrew, yield_unit_`. `limit` clamped 1-50 (default 25).

**Client**
- `HttpStorageAdapter.search<T>()` / `StorageService.search<T>()` — mirrors
  `query()`/`queryFiltered()`'s shape; localStorage fallback path filters in-memory
  with the same `filterOptionsByStartsWith` semantics (dev/demo mode unaffected).
- `ProductDataService.searchProducts()` — calls `storage.search()`, normalizes each
  lean row through the existing `normalizeProduct()` so callers get a fully-typed
  `Product` with sane defaults for anything the lean projection omitted.
- `RecipeDataService.searchRecipes()` — thin passthrough (RecipeDataService doesn't
  normalize on the read path either, matching its existing `loadInitialData()`).
- `ingredient-search.component.ts` (recipe-builder) — replaced the full
  `products_()`/`recipes_()` computed-filter with `toObservable` +
  `debounceTime(250)` + `switchMap` calling both searches in parallel, `toSignal`'d
  back. Exclude-already-in-recipe filtering kept as a separate `computed()` layer so
  it doesn't trigger a new network call. Added a 2-char minimum (matches
  `preparation-search.component.ts`'s existing minimum, per plan).
- `recipe-book-list.component.ts`'s `filteredProductsForIngredientSearch_` — same
  debounce/switchMap treatment over `ProductDataService.searchProducts()`.

## Verify

- `ng build --configuration production` — passes (pre-existing bundle-budget
  warnings only, unrelated to this change).
- `curl .../PRODUCT_LIST/search?q=עגב` / `.../RECIPE_LIST/search?q=פי` — correct
  prefix matches, lean shape, 13-19ms. `KITCHEN_SUPPLIERS/search` → 403. Empty `q` →
  `[]`.
- Live in the running app (`dev-guest`/"Guest Admin" account — 1,478 products, 2,113
  recipes/dishes, the actual legacy-imported catalog):
  - recipe-book ingredient filter: typed "עגב" → exactly one
    `GET .../PRODUCT_LIST/search` request (32ms), dropdown populated, no full
    `PRODUCT_LIST` GET.
  - recipe-builder ingredient search: typed "עגב" → exactly one
    `GET .../PRODUCT_LIST/search` + one `.../RECIPE_LIST/search` (6-9ms each, run in
    parallel), dropdown showed products then the matching recipe with its type pill,
    plus the "add new" fallback. Selected a product result → row populated
    `name_hebrew` **and** `unit` (`גרם`) correctly — confirms the lean projection's
    `base_unit_`/`purchase_options_` fields round-trip through `onItemSelected()`.
  - No console errors introduced by this change. (Pre-existing, unrelated: recurring
    `ERR_CONNECTION_REFUSED` every ~20s regardless of navigation, and a 404 on
    `/assets/images/add_ingrediant.png` referenced in the same component's
    "add new" row icon — both predate this session's edits, not touched.)
