Audit + master plan — nothing changed yet

Making FoodVibe feel like one product

I loaded all 13 screens side by side and measured each one at three real viewport widths — 390 (phone), 768 (tablet), 1440 (desktop) — then read every file for tokens, states, icons, breakpoints and accessibility. Below: the verdict, every defect I found with the screen it lives on, the target system, and the execution plan with a sign-off list.

The good news
  • Zero layout breaks. No horizontal overflow, no clipped text, no overlapping elements on any screen at any of the three widths.
  • Token discipline is high. 179–473 var(--…) uses per screen; almost no stray hex.
  • Page width, padding, titles, radius, buttons and shadows were already unified in the previous pass.
What still separates us from the top tier
  • The app has no shared shell — nav and background are copy-pasted 13 times and have already drifted.
  • 9 different breakpoints across 13 files. Two screens have none at all.
  • Mobile is desktop-shrunk, not designed: 36px controls, no bottom tab bar, 7–151 sub-44px targets per screen.
  • No loading, error or focus-state system, and zero accessibility labels app-wide.
  • 300+ hand-drawn inline SVG icons instead of the mandated Lucide set.

1 — Defect register

Measured, not guessed. Severity: P1 breaks the one-product feeling or usability · P2 visible side by side · P3 polish.

P1 1. No app shell — the chrome is duplicated 13 times

Every screen carries its own copy of the top nav, the ambient gradient and the nav link list. It has already drifted: Inventory, Recipe Builder and Venue Detail have no self-link, so their active pill renders differently from the other ten. Recipe Builder and Cook View are missing from the nav entirely — Recipe Builder is only reachable from Recipe Book, Cook View only from Recipe Book. Venue Detail is reachable only from Venues. Ten nav items is also past the point where a flat pill row works.

Fix: one AppShell component holding nav + gradient + page header, imported by all 13 screens, driven by a single nav list with a current prop. One place to change nav forever after. Group the 10 items into 3 sections (Kitchen · Catalog · Setup).
P1 2. Nine breakpoints, two screens with none

In use today: 480, 599, 640, 699, 700, 768, 860, 900, 1023. The design system defines exactly two edges (767 / 1023). Result: resize the browser and each screen reflows at a different moment. Venues and Venue Detail have zero media queries — Venue Detail keeps a 260px sidebar column down to phone width.

Fix: exactly three edges everywhere — ≤479 small phone (optional density step), ≤767 mobile, ≤1023 tablet. Every other value is rewritten to the nearest edge. Venues and Venue Detail get real mobile layouts.
P1 3. Mobile is a shrunk desktop, not a designed screen
  • At 390px I counted controls below the 44px minimum on every screen: Inventory 151, Recipe Book 81, Recipe Builder 80, Equipment 58, Suppliers 52, Metadata 49, Menu Intelligence 41, Menu Library 31, Trash 25, Dashboard 16, Cook View 16, Venues 7, Venue Detail 7. Nav pills are 36px tall on all of them.
  • The design system specifies a bottom tab bar (3.5rem, safe-area aware) on mobile. No screen has one — all 13 use a horizontally scrolling pill row where items 6–10 are invisible until you scroll.
  • Mobile card mode for data tables is built with 46–59 !important overrides per file (Inventory 49, Recipe Book 59, Equipment 50, Suppliers 46) fighting the desktop inline styles. It works, but any future edit is a coin flip.
  • Off-scale type at phone size: 8px and 11px on Inventory, Recipe Book, Suppliers, Equipment — below the 12px floor.
Fix: a real mobile spec — bottom tab bar with the 5 primary destinations (rest under "More"), 44px minimum on every tappable element, 12px type floor, and card mode expressed as its own layout branch instead of !important patches.
P1 4. No state system — loading, empty, error, focus
  • Loading: nothing, anywhere. Not one skeleton in 13 screens. Top-tier products all show structure before data.
  • Empty states missing on Dashboard, Recipe Builder, Menu Intelligence, Metadata Manager; the ones that exist (Inventory, Recipe Book, Suppliers, Equipment, Trash, Menu Library) are each hand-written differently.
  • Error / validation states exist only as a red border in a couple of modals. No field error text, no failed-save path.
  • Focus rings: present on 9 screens, absent on Dashboard, Cook View, Venue Detail. Keyboard users lose the caret there.
  • Zero prefers-reduced-motion blocks, though the system requires it.
Fix: four shared patterns — skeleton row/card, empty state (icon + line + optional action), inline field error, and one focus ring token applied globally. Plus one reduced-motion block in the shell.
P2 5. Icons are hand-drawn, not a set

Between 10 and 38 inline <svg> per screen — over 300 in total — and zero Lucide, which the design system mandates and the codebase lints for. Stroke weight, corner treatment and optical size therefore vary from screen to screen, which is exactly the thing that makes an app read as "assembled" rather than "designed". None of them carry a label, so a screen reader announces nothing.

Fix: load Lucide once in the shell, replace the inline set with named Lucide icons at 16/22px, 1.5 stroke, currentColor. Icon-only buttons get an aria-label in the same pass.
P2 6. Cook View lives in a different product

Dark palette (#0a1614, #0f2e2a, #5eead4), 29 raw rgba() values, 123 token uses against 400+ on comparable screens, its own nav that is not the app nav, its own breakpoint (860), no focus states, a 20px-tall back link and 27px stepper buttons. As a deliberate hands-free kitchen mode a dark theme is defensible — but then it needs to be a declared mode of the same system, not an exception.

Fix (your call, see questions): either (a) promote it to an official Kitchen mode — dark tokens added to the system, same shell, same components, 56px touch targets for wet hands; or (b) bring it back to the light glass system like everything else.
P2 7. Motion is declared but barely used

The system defines two easings, three durations, hover lift, press scale and seven entrance keyframes. In the files: transition: appears 0–5 times per screen and 5 of 13 screens have none. There is no page-enter animation, no card-in stagger, no modal transition. The app feels static next to the products we are benchmarking against. Metadata Manager also hand-writes a raw cubic-bezier instead of the token.

Fix: a motion pass — pageEnter on the content column, cardIn stagger on grids/lists, hover lift + press scale on every card and button, modal in/out, all on the two token easings, all disabled under reduced motion.
P3 8. Residue
  • Stray hex values: Recipe Book and Recipe Builder repeat #14b8a6 #10b981 #a0833f #0ea5e9 — all four are tokens. Metadata Manager hardcodes six label colors that belong in a token set. Cook View has seven.
  • Nav pill font is a literal 13px in all 13 files — consistent by luck, not by token.
  • Venue Detail is the thinnest screen: no transitions, no easing tokens, no toast system, no focus ring, no breakpoints. It reads like a draft next to Venues.
  • Carousel arrows on the data screens use an 11px glyph in a 20px hit area.

3 — The target system

One page anyone on the team can hold in their head. Everything in the plan below serves this.

Shell

One AppShell: ambient wash, frosted top nav (desktop/tablet), bottom tab bar (mobile), page header slot, toast host. Screens supply only content.

Breakpoints

≤479 compact phone · ≤767 phone · ≤1023 tablet · ≥1024 desktop. Three widths: 1520 data · 1200 standard · 720 narrow.

Controls

Desktop 38px, mobile 44px minimum — every button, pill, input, icon button, row action. Type floor 12px.

States

Every list and form ships five: default · loading skeleton · empty · error · success/toast. Focus ring token on every interactive element.

Icons

Lucide only. 16px inline, 22px nav, 1.5 stroke, currentColor. Icon-only buttons always labelled.

Motion

Two easings, three durations. Page enter, card stagger, hover lift −2px, press 0.97, modal in/out. Clamped under reduced motion.

5 — Validation list (definition of done)

  1. All 13 screens import one shell; the nav list exists in exactly one place; every screen highlights itself.
  2. Grep finds only 479, 767, 1023 as breakpoint values. No screen without media queries.
  3. At 360 and 390: zero horizontal overflow, zero clipped text, zero tappable elements under 44px, no type under 12px.
  4. At 768 and 1440: zero overflow, content column at one of the three approved widths.
  5. Every list screen demonstrates loading, empty and error states; every form field can show an error.
  6. Every interactive element has a visible focus ring; tab order walks each screen sensibly.
  7. Every icon is Lucide; every icon-only control has an accessible label; every image has alt.
  8. No stray hex outside the token file; no font-size literal below 12px; !important count under 5 per file.
  9. Hover lift, press scale and page-enter present on every screen; everything clamps under reduced motion.
  10. Screenshot sheet: 13 screens × 3 widths, reviewed side by side as one family.
